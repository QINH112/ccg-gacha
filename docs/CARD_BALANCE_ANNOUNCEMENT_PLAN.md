# 卡牌平衡调整与云公告开发计划

> 文档状态：功能实施与自动化验证完成，等待云端部署及真机视觉确认
> 当前版本：v1.3
> 建立日期：2026-11-18
> 维护规则：每次确认需求、实施变更、完成验证或发现风险后更新本文档。

## 1. 目标

为《卤蛋传说》建立可长期维护的卡牌平衡调整流程：卡牌数值与效果由现有云端卡牌配置更新；主界面新增“卡牌调整”入口；玩家点击后查看由云数据库发布的调整公告，并能清楚对比每张卡牌修改前后的费用、攻击、生命、关键词和效果文本，同时在每张调整卡片右侧展示该卡发布时的立绘。

本次首批调整包含三张卡牌：

| 卡牌 ID | 卡牌 | 修改前 | 修改后 | 已确认说明 |
| --- | --- | --- | --- | --- |
| `c001` | 星尘学徒 | 1 费 1/2，无效果 | 1 费 1/3，无效果 | 只修改生命值 |
| `c002` | 月影侍从 | 1 费 2/1，无效果 | 1 费 3/1，无效果 | 只修改攻击力 |
| `r009` | 归墟歌者 | 4 费 3/3；亡语：对所有敌方随从造成 1 点伤害 | 4 费 4/4；城墙；保留原亡语 | 用户所说“嘲讽”统一使用游戏现有名称“城墙”，底层关键词为 `guard` |

## 3. 已确认决策

1. 卡牌 ID 不变，避免破坏收藏、牌组、日志和玩家存档引用。
2. “嘲讽”不新增第二套关键词，沿用现有 `guard`，玩家界面显示“城墙”。
3. 归墟歌者保留现有亡语，只增加城墙并调整为 4/4。
4. 主界面新增“卡牌调整”按钮。
5. 点击按钮后显示修改前与修改后的对比，而不是只显示一句公告文本。
6. 公告内容由云数据库配置，后续平衡调整不需要修改前端公告内容。
7. 产品行为已确认并完成实施；后续变更继续先更新本文档，再调整权威数据与公告配置。

## 4. 推荐云数据模型

建议新建集合 `balanceNotices`，每次平衡更新保存一条独立公告。卡牌运行数据仍保存在现有 `cards` 集合，公告只负责展示历史快照，不能作为战斗结算数据源。

```js
{
  id: "balance-20261118-01",
  title: "卡牌平衡调整",
  summary: "三张卡牌完成数值与关键词调整",
  version: 1,
  publishedAt: 1794950400000,
  enabled: true,
  changes: [
    {
      cardId: "c001",
      name: "星尘学徒",
      artPath: "subpackages/card-art-base/images/c001.jpg",
      originalCraftCost: 40,
      originalShinyCraftCost: 120,
      before: {
        cost: 1,
        attack: 1,
        health: 2,
        keywords: [],
        rulesText: ""
      },
      after: {
        cost: 1,
        attack: 1,
        health: 3,
        keywords: [],
        rulesText: ""
      },
      note: "生命值提高 1 点"
    }
  ]
}
```

### 字段约束

- `id`：人工指定、全局唯一，发布后不可复用。
- `publishedAt`：首次调用 `enableBalanceNotice` 时由服务器覆盖为实际启用时间，用于公告排序、玩家红点和 30 天原价分解窗口；草稿提交值不作为正式发布时间。
- `firstEnabledAt`：不可变的首次正式启用时间。草稿为 `0`；首次启用时与 `publishedAt` 写入相同的服务端时间；关闭和重新启用均不得修改。
- 公告首次启用后 `publishedAt` 永久保持不变；关闭后重新启用只恢复可见状态，不重置排序时间、红点发布时间或 30 天原价分解窗口。
- `enabled`：允许管理员临时隐藏公告。
- `changes`：必须保存完整前后快照；不能运行时拿当前卡牌数据反推“修改前”。
- `originalCraftCost`：调整正式发布前的非闪版本完整合成成本，必须在公告发布时固化，不能由发布后的当前配置反推。
- `originalShinyCraftCost`：调整正式发布前的闪卡版本完整分解原价，通常为 `originalCraftCost * 3`，必须在公告发布时固化。
- `cardId`：用于关联卡牌，但即使以后卡名变化，历史公告仍使用发布时的 `name` 快照。
- `artPath`：发布时使用的卡牌立绘路径，默认来自对应卡牌的 `artPath`，必须随公告保存，不能只依赖未来卡牌数据。
- `keywords`：保存底层稳定值，例如 `guard`；前端统一映射为“城墙”。
- `rulesText`：保存玩家可读效果文本，空效果允许使用空字符串。

### 推荐读取规则

1. `gameData` 云函数在首次加载时读取公告，避免主界面额外调用云函数。
2. 只返回前端实际需要的安全展示字段。
3. 没有公告、公告全部关闭或集合尚未创建时，游戏主体仍可正常进入，主界面入口保持显示。
4. 没有启用公告时，点击入口提示“暂无卡牌调整公告”。
5. 公告读取失败不得覆盖卡牌配置加载成功的结果；点击入口应提示“卡牌调整公告加载失败，请稍后重试”，不能误报为没有公告。

### 红点与云端已读状态

- 在现有 `gameSaves` 玩家存档中增加 `uiState.lastReadBalanceNoticeId`，默认空字符串。
- 首次加载时，若存在最新启用公告，且其 `id` 不等于 `lastReadBalanceNoticeId`，主界面显示红点。
- 玩家真正打开最新公告详情后，前端调用云函数；云函数再次确认该 ID 仍是最新启用公告，再写入玩家存档。
- 只进入公告历史列表不清除红点；打开旧公告也不清除红点。
- 管理员发布新公告必须使用新 ID，因此新公告上线后所有玩家会重新看到红点。
- 已发布公告不可复用 ID；关闭最新公告后，系统以当前最新启用公告计算红点。
- 云端写入失败时公告仍可阅读，但红点保持，下一次打开最新公告时重试。
- 已读状态不记录在本地缓存，保证同一微信账号跨设备同步。

### 最新公告与历史公告方案对比

| 方案 | 玩家体验 | 云端结构 | 前端复杂度 | 后续扩展 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 只展示最新一条 | 点击后立即看到当前调整，最简单 | 集合中仍可保留多条，但接口只返回最新启用项 | 低 | 今后增加历史页时需要再改接口和页面 | 可用，但扩展成本较高 |
| 历史列表，默认打开最新 | 玩家可核对历次平衡变化 | 每次发布独立文档，按 `publishedAt` 降序 | 中 | 天然支持追溯、回滚说明和多次调整同一卡牌 | **已确认采用** |

采用“一次调整一条独立文档”的历史型数据结构。玩家点击主界面入口后默认打开最新启用公告，可返回公告列表查看往期启用公告。

推荐的兼容接口形态：

```js
{
  balanceNotices: {
    latest: { /* 最新启用公告的安全展示字段 */ },
    items: [ /* 按 publishedAt 降序排列的启用公告摘要与内容 */ ]
  }
}
```

`latest` 与 `items[0]` 必须指向同一公告。历史公告按 `publishedAt` 降序排列；相同时间戳时使用 `id` 做稳定排序。已发布历史公告不得覆盖修改；需要纠正时发布新公告并在摘要中说明。

## 5. 主界面与公告界面方案

### 主界面入口

- 当前主界面为整张美术坐标布局，入口不能只在旧版按钮数组中追加。
- 玩家可见名称统一使用素材上的“调整公告”；功能与数据仍称为“卡牌平衡调整公告”。
- 正式运行时素材使用 `assets/ui/home/adjustAnnouncement.png`（152 × 141 px，透明通道）；用户提供的 `adjustAnnouncement@4x.png` 为 608 × 564 px 四倍母版，两者比例一致且视觉内容已核对一致。
- 素材设计说明见 `docs/HOME_BUTTON_ADJUST_ANNOUNCEMENT.md`。
- 新入口必须在 `HOME_ART_RECTS` / `HOME_MENU_ART` 或等价布局配置中拥有独立安全区域。
- 入口不得遮挡右上角微信胶囊、卡池、抽卡按钮、现有功能入口和开发阶段重置入口。
- 入口始终显示，避免公告开关导致主界面布局跳动。
- 没有启用公告时仍可点击，提示“暂无卡牌调整公告”。
- 公告读取失败时仍可点击，提示“卡牌调整公告加载失败，请稍后重试”。
- 入口需要显示新公告红点。
- 玩家打开最新公告详情并成功写入云端已读状态后，红点消失；只看列表或旧公告不消失。

### 主界面排布候选

当前美术首页第一排为 5 个入口（每日签到、召唤记录、卡牌图鉴、卡牌工坊、商店），第二排为 6 个入口（邮箱、每日任务、成就、我的牌组、对战、对战记录）。

推荐方案：将“调整公告”放在第一排末尾，第一排 6 个入口统一缩放并重新等距排列；第二排 6 个入口的位置和顺序保持不变。这样上下两排数量对称，也最大限度减少现有点击区域变化。

建议顺序：

```text
第一排：每日签到 / 召唤记录 / 卡牌图鉴 / 卡牌工坊 / 商店 / 调整公告
第二排：邮箱 / 每日任务 / 成就 / 我的牌组 / 对战 / 对战记录
```

所有按钮仍使用 141 px 设计高度，仅按可用宽度等比缩小宽度和高度，并以各自中心点对齐；红点绘制在“调整公告”按钮右上角内侧，不能超出透明素材边界或与相邻按钮重叠。

### 公告展示

- 标题、发布日期、摘要来自云配置。
- 点击主界面入口后默认打开最新启用公告。
- 公告详情提供“返回公告列表”，列表按发布日期从新到旧排列。
- 点击列表项进入对应历史公告详情；从详情返回时保留列表滚动位置。
- 历史列表每条公告显示原价分解状态：只要该公告至少一张卡仍使用该公告的有效窗口，显示“原价分解进行中”；若所有卡均已到期或已被更新公告替代，显示“原价分解已结束”。
- 列表只显示公告级状态，具体卡牌截止时间在公告详情的各调整卡片中显示。
- 历史列表保持上述二态，不额外显示“已被替代”；自然到期与更新调整替代的区别只在详情中逐卡说明。
- 每项调整至少显示卡名及费用、攻击、生命、关键词、效果文本的前后对比。
- 每项调整卡片右侧显示该条记录保存的 `artPath` 立绘；立绘区域对应用户确认的右侧空白区域，不改变左侧前后数值对比布局。
- 立绘保持原始宽高比并采用居中裁剪填满（cover），不得拉伸变形；超出右侧立绘区域的部分裁掉。
- 立绘区域使用轻微圆角，并在靠近左侧数据区的一边增加渐隐，避免图像与费用、攻击、生命、关键词和效果文字争抢可读性。
- 375px、430px 等窄屏均保留右侧立绘；立绘宽度最多约占调整卡片内容宽度的 28%。空间不足时优先缩小立绘，左侧数据区拥有更高布局优先级，立绘不得覆盖文字。
- 保持现有纵向调整卡片结构，不因加入立绘改成横向分页、轮播或独立卡牌详情。
- 公告立绘仅用于视觉识别，不响应点击或长按，也不打开图鉴卡牌详情；立绘区域的触摸继续交给公告纵向滚动处理。
- 公告始终展示卡牌基础立绘，不叠加闪卡虹彩、流光或闪卡卡框；卡牌调整同时作用于非闪版本与闪卡版本，立绘不得暗示只调整其中一个版本。
- 每张调整卡片显示原价分解期限。有效期内显示“原价分解截止：YYYY-MM-DD HH:mm”，时间为 `firstEnabledAt + 30 天` 的北京时间；非闪版本与闪卡版本共用同一截止时间。
- 窗口结束后显示“原价分解已结束”。历史公告仍保留期限或结束状态，方便玩家核对；客户端不得使用本地保存的旧倒计时决定实际返还金额，最终资格由工坊云函数的服务端时间判断。
- 若同一卡牌的新调整公告已经正式启用，旧公告中该卡显示“原价分解已由更新调整替代”，不得显示仍有效的旧截止时间，也不得与自然到期状态混淆。
- 公告关闭后重新启用仍使用首次 `firstEnabledAt` 计算并显示原截止时间；若已超过该时间，只显示“原价分解已结束”，不得生成或展示新的截止日期。
- 立绘加载失败时保留调整文字和数值对比，使用空白/占位区域，不阻塞公告滚动和关闭操作。
- 只突出发生变化的字段，未变化字段保持可读但不制造误导。
- 归墟歌者应明确显示“新增：城墙”，同时显示亡语保持不变。
- 长公告支持纵向滚动；关闭按钮和内容区域避开顶部胶囊安全区与底部手势区。
- 云配置异常时显示简短可理解提示，不向玩家展示云函数堆栈。

## 6. 数据更新与兼容策略

1. 修改 `initGameData` 中三张卡牌的权威设计定义。
2. 沿用现有安全同步流程更新 `cards` 集合，不删除或重建玩家数据。
3. 对三张卡牌执行更新前后字段断言，防止错误覆盖其他卡牌。
4. 已保存牌组继续引用相同卡牌 ID，不要求玩家重新组牌。
5. 已开始对局使用对局快照继续完成；新数值只影响更新后新建的对局。
6. 收藏数量、闪卡数量、卡池归属、稀有度、合成与分解价值保持不变。

### 权威数据说明

- 运行时卡牌数据以 `cloudfunctions/initGameData/index.js` 中合成后的卡牌模板及云端 `cards` 集合为准。
- `docs/CARD_DESIGN_PLAN.md` 保留重设计阶段的旧源数据、候选提案、讨论快照和当时的最终设计表，并持续记录后续新卡牌与新机制；历史旧数值不能直接用于当前部署。
- 当前卡牌修改采用“两阶段发布”：先读取调整前卡牌并创建 `enabled:false` 公告草稿，固化 `before`、`originalCraftCost`、`originalShinyCraftCost` 和 `artPath`；再更新 `cloudfunctions/initGameData/index.js` 或云端 `cards` 集合，完成校验后启用公告。
- `docs/CARD_DESIGN_PLAN.md` 中的历史旧表不因后续平衡调整反复改写；新的数值变化记录在本计划的调整表、公告文档和变更日志中，新卡牌设计则持续写入卡牌设计文档。
- 公告中的 `before` / `after` 是发布快照；即使未来再次调整同一张卡，也不得回写旧公告。

## 8. 卡牌调整与公告发布标准操作手册

本节是今后每次卡牌平衡调整的权威操作流程。必须采用“两阶段发布”：先保存不可见公告草稿并固化调整前数据，再更新卡牌；确认云端数据正确后才启用公告。这样既避免玩家提前看到公告，也保证 30 天原价分解所需的调整前成本不会丢失。

### 8.1 发布前准备

每次调整开始前先确定以下内容：

1. 为本次调整分配唯一公告 ID，格式建议为 `balance-YYYYMMDD-序号`，例如 `balance-20261118-01`。
2. 记录每张卡牌修改前的完整快照：`cost`、`attack`、`health`、`keywords`、`rulesText`。
3. 记录每张卡牌调整前的完整合成成本 `originalCraftCost`、其 3 倍 `originalShinyCraftCost`，以及当前 `artPath`。
4. 确认修改后的完整快照和玩家可理解的调整说明。
5. 不修改卡牌 `id`。收藏、牌组、日志和对局均依赖原 ID。
6. 草稿中的 `publishedAt` 仅可作为计划发布时间提示；首次调用 `enableBalanceNotice` 时由服务器覆盖为实际启用时间，该服务端时间才是 30 天窗口起点。
7. 底层关键词只能使用：`guard`、`charge`、`rush`、`shield`、`lifesteal`、`battlecry`、`deathrattle`、`aura`；玩家界面分别显示城墙、冲锋、突袭、护盾、吸血、入场、亡语、光环。

### 8.2 第一阶段：保存不可见公告草稿

1. 在修改任何目标卡牌前调用 `adminGame.upsertBalanceNotice`。
2. 公告必须使用新 ID，并设置 `enabled:false`。
3. 管理员每项调整只提交 `cardId`、计划中的 `after` 和玩家可读 `note`；`name`、`before`、`artPath`、`originalCraftCost`、`originalShinyCraftCost` 全部由服务器从当前 `cards` 与 `gameConfig` 读取并固化。
4. 管理员提交的 `name`、`before`、`artPath`、`originalCraftCost`、`originalShinyCraftCost` 即使存在也必须忽略或拒绝，绝不能覆盖服务端读取到的调整前事实。
5. 同一公告的 `changes[]` 中 `cardId` 必须唯一；发现重复卡牌时直接拒绝创建草稿，不得自动去重或选择其中一项。
6. 每项 `after` 必须与服务器读取的 `before` 至少有一个业务字段发生变化；比较字段为 `cost`、`attack`、`health`、去重后的关键词集合和 `rulesText`。完全一致时拒绝创建草稿，不得仅靠 `note` 制造调整记录。
7. 草稿创建后不得用相同 ID 覆盖；发现错误时废弃该草稿并创建新 ID。
8. 草稿的 `firstEnabledAt` 固定为 `0`，不进入玩家公告列表、不产生红点，也不能开启 30 天原价分解窗口；草稿中的 `publishedAt` 不具备业务效力。

### 8.3 第二阶段：修改权威卡牌设计

适用于正式版本和平衡补丁，可确保重新初始化环境时仍保留正确数据。

1. 打开 `cloudfunctions/initGameData/index.js`。
2. 在 `CARD_DESIGNS` 中修改目标卡牌的费用、攻击、生命、规则文字、关键词和效果结构。
3. 如果新增或修改实际战斗效果，同步核对 `effects`，不能只修改展示用的 `rulesText`。
4. 在 `tools/test_card_designs.js` 增加或更新目标卡牌的精确断言。
5. 关键词组合或效果发生变化时，在 `tools/test_battle_engine.js` 增加对应战斗行为测试。
6. 本地运行卡牌数据测试和战斗回归测试。
7. 在微信开发者工具中重新上传并部署 `initGameData`，选择“上传并部署：云端安装依赖”。
8. 手动调用一次 `initGameData`，参数使用 `{}`，不要使用 `force`。
9. 进入云开发控制台的 `cards` 集合，按卡牌 ID 核对已修改字段。

本次三张牌在 `CARD_DESIGNS` 中应为：

```js
c001: design(1, 1, 3, ""),
c002: design(1, 3, 1, ""),
r009: design(
  4,
  4,
  4,
  "城墙；亡语：对所有敌方随从造成 1 点伤害。",
  ["guard", "deathrattle"],
  [damage("deathrattle", "all-enemy-minions", 1)]
)
```

安全调用 `initGameData` 的参数：

```json
{}
```

该同步会按现有卡牌 ID 更新 `cards` 权威数据，不会清空玩家的 `gameSaves`、收藏、货币或牌组。已经开始的对局继续使用原对局快照，新建立的对局使用新卡牌数据。

### 8.4 临时方式：管理员修改单张卡牌

仅适用于紧急修正。长期权威值仍必须同步写回 `cloudfunctions/initGameData/index.js`，否则以后重新初始化时可能恢复成旧设计。

调用云函数 `adminGame`，每张卡分别执行一次。例如：

```json
  "data": {
    "cost": 1,

    "health": 3,
    "keywords": [],
    "effects": [],
    "rulesText": ""
  }
```

归墟歌者必须同时提交 `guard`、`deathrattle` 和原亡语效果，不能只修改文字：

```json

  "secret": "替换为你的 INIT_SECRET",
  "id": "r009",
```

### 8.5 草稿创建与正式启用

修改卡牌前先使用以下模板创建不可见草稿；首次三张卡牌调整示例：

```json
{
  "action": "upsertBalanceNotice",
  "secret": "替换为你的 INIT_SECRET",
  "data": {
    "id": "balance-20261118-01",

      {
        "cardId": "c001",

        "artPath": "subpackages/card-art-base/images/c001.jpg",

        "before": {
          "cost": 1,

        },
        "after": {
          "cost": 1,

        },

      },
      {
        "cardId": "c002",
        "name": "月影侍从",
        "before": {
          "cost": 1,
          "attack": 2,
          "health": 1,
          "keywords": [],

        },
        "after": {
          "cost": 1,
          "attack": 3,

          "rulesText": ""
        },

```

草稿创建成功后，云函数返回结果中应包含已由服务端固化的 `before`、`originalCraftCost`、`originalShinyCraftCost` 与 `artPath`。完成卡牌更新并核对云数据库后，再正式启用：

```json
{
  "action": "enableBalanceNotice",
  "secret": "替换为你的 INIT_SECRET",
  "id": "balance-20261118-01"
}
```

调用 `enableBalanceNotice` 时，服务器必须先读取每张目标卡的当前云端数据，并与公告 `after` 中的 `cost`、`attack`、`health`、`keywords`、`rulesText` 逐项比较。关键词比较采用去重后的稳定集合语义，不因数组顺序不同误判；其他字段必须精确一致。任一字段不一致时启用失败，公告继续保持草稿状态，并返回具体卡牌 ID 与不一致字段。

服务器还必须校验每张调整记录的 `artPath`：它必须与当前卡牌 `artPath` 完全一致，并符合 `subpackages/card-art-*/images/<cardId>.jpg` 格式。路径缺失、卡牌 ID 不匹配或分包路径不一致时拒绝启用。服务端只能验证路径与卡牌数据契约；客户端运行时若图片仍加载失败，则仅隐藏或占位立绘区域，公告文字、滚动、返回和关闭保持可用。

全部卡牌校验通过后，首次正式启用时服务器才将 `publishedAt` 与 `firstEnabledAt` 同时写为同一个当前服务端时间。正式启用成功后，云函数返回结果中应包含：

```json
{
  "notice": {
    "id": "balance-20261118-01",
    "enabled": true,
    "firstEnabledAt": 1794974400000,
    "publishedAt": 1794974400000
  }
}
```

每次新公告都必须更换 `data.id`。已发布 ID 不允许覆盖；即使只是修改错别字，也应关闭旧公告并使用新 ID 发布更正公告，从而保留完整历史。

### 8.6 启用、关闭与重新启用公告

关闭公告不会回滚卡牌数据，只会使该公告不再出现在玩家公告列表中：

```json
{
  "action": "disableBalanceNotice",
  "secret": "替换为你的 INIT_SECRET",
  "id": "balance-20261118-01"
}
```

重新启用已有公告：

```json
{
  "action": "enableBalanceNotice",
  "secret": "替换为你的 INIT_SECRET",
  "id": "balance-20261118-01"
}
```

重新启用时必须保留第一次正式启用写入的 `publishedAt` 与 `firstEnabledAt`；不得覆盖为当前时间，也不得重新开始或延长 30 天原价分解窗口。

公告首次启用后，其对应卡牌的 30 天原价分解资格与公告当前可见状态分离：`enabled:false` 只从公告列表隐藏该记录，不取消已经开始的补偿窗口。工坊以 `firstEnabledAt > 0` 判断公告曾正式生效，并以该时间计算窗口；窗口仅在自然到期或同一卡的新调整公告正式启用后失效。

### 8.7 发布后验证清单

1. 在 `cards` 集合按 ID 检查费用、攻击、生命、`keywords`、`effects`、`rulesText`。
2. 在 `balanceNotices` 集合确认新公告存在，`enabled` 为 `true`，`publishedAt` 为有效毫秒时间戳。
3. 重新进入游戏，确认主界面“调整公告”出现红点。
4. 点击按钮，确认默认打开最新公告，三张牌的修改前后数据正确。
5. 返回历史列表，确认公告按 `publishedAt` 从新到旧排列。
6. 打开最新公告后重新进入游戏，确认同一账号红点已经消失。
7. 在卡牌图鉴和新建对局中确认新数据已经生效。
8. 已开始的旧对局应继续使用创建对局时保存的快照。

如果点击按钮提示“暂无卡牌调整公告”，依次检查：

1. `gameData`、`adminGame`、`initGameData` 是否均已部署为最新版本。
2. 云数据库是否存在 `balanceNotices` 集合。
3. 集合中是否至少存在一条 `enabled: true` 的公告。
4. 调用 `initGameData` 时是否使用了安全参数 `{}`。
5. 重新编译并重新进入游戏，使客户端重新调用 `gameData.load`。

### 8.8 回滚规则

1. 公告内容错误但卡牌数据正确：关闭错误公告，使用新 ID 发布更正公告。
2. 卡牌数据错误：先在权威设计中修正卡牌，重新部署并安全调用 `initGameData`，核验云端数据后发布新的回滚说明公告。
3. 不得直接改写旧公告的 `before` / `after`，否则会破坏历史记录。

### 8.9 首期公告一次性受控迁移

用户已授权仅对既有公告 `balance-20261118-01` 执行一次受控迁移，用于补齐新规则上线前未保存的原价与立绘字段。

| 卡牌 ID | 稀有度 | `artPath` | `originalCraftCost` | `originalShinyCraftCost` |
| --- | --- | --- | ---: | ---: |
| `c001` | 普通稀有度 | `subpackages/card-art-base/images/c001.jpg` | 40 | 120 |
| `c002` | 普通稀有度 | `subpackages/card-art-base/images/c002.jpg` | 40 | 120 |
| `r009` | 稀有稀有度 | `subpackages/card-art-base/images/r009.jpg` | 100 | 300 |

迁移约束：

1. 只允许目标公告 ID 为 `balance-20261118-01`。
2. 只补充三张卡的 `artPath`、`originalCraftCost` 与 `originalShinyCraftCost`。
3. 必须保留公告原 `id`、首次 `publishedAt`、`enabled` 状态、标题、摘要、版本以及完整 `before` / `after` / `note`；迁移时为该已发布公告补入与原 `publishedAt` 相同的 `firstEnabledAt`。
4. 迁移不得触发红点发布时间变化，不得重新开始或延长 30 天原价分解窗口。
5. 首期公告保留原发布时间 `2026-11-18 12:00:00`（北京时间），30 天原价分解窗口固定于 `2026-12-18 12:00:00`（北京时间）结束；即使迁移功能稍后上线，也不补足新的 30 天。
6. 重复执行必须幂等：字段已经等于权威值时不重复修改；字段存在但与迁移表冲突时停止并报错，不得静默覆盖。
7. 迁移完成后必须重新读取公告并逐字段核对，同时验证三张立绘文件存在。
4. 不得通过删除或重建 `gameSaves` 实现卡牌回滚。
5. 不得使用 `force:true` 进行普通平衡发布；强制模式可能覆盖更多权威配置，只能在明确了解影响并完成备份时使用。

## 10. 高标准验收标准

1. 云数据库中修改公告后，重新进入游戏即可看到新内容，无需修改公告展示代码。
2. 首次公告准确展示三张卡牌的完整前后快照，不允许用修改后的当前数据冒充旧数据。
3. 星尘学徒、月影侍从、归墟歌者在云端 `cards` 集合、卡牌图鉴、牌组编辑和新对局中保持一致。
4. 归墟歌者同时具备城墙与原亡语；城墙目标限制和亡语伤害均通过自动化回归。
5. 其他 69 张卡牌的费用、身材、关键词、效果和 ID 不发生非预期变化。
6. 玩家收藏、闪卡、牌组、货币、任务、签到、邮件、抽卡保底和对战记录不被清空或重置。
7. 更新前已开始的对局能按原快照继续；更新后新对局使用新卡牌数据。
8. 公告集合不存在、没有启用公告或公告全部关闭时，游戏主体仍可使用，入口仍显示并提示“暂无卡牌调整公告”。
9. 公告读取失败时，游戏主体仍可使用，入口提示“卡牌调整公告加载失败，请稍后重试”，不与空公告混淆。
10. 公告超过一屏时可完整滚动阅读；关闭交互可靠；按钮和弹层不与微信胶囊及安全区冲突。
11. 玩家界面只显示可理解错误，不显示云函数堆栈、数据库内部信息或管理员字段。
12. 数据测试、战斗引擎测试、前端烟雾测试全部通过，并在本文档记录命令与结果。
13. 管理员发布下一次调整时有明确、可重复的云数据库操作步骤和模板。
14. 同一账号在设备 A 阅读最新公告后，设备 B 重新进入游戏不再显示该公告红点；发布新 ID 公告后两台设备均重新显示红点。
15. 只进入历史列表、阅读旧公告或已读写入失败时，不得错误清除最新公告红点。

## 11. 风险台账

| 风险 | 影响 | 缓解措施 | 状态 |
| --- | --- | --- | --- |
| 公告只引用当前卡牌数据，导致历史“修改前”丢失 | 历史公告失真 | 公告保存完整 `before` / `after` 快照 | 已验证 |
| 主界面为美术坐标布局，新增按钮遮挡现有 UI | 手机端不可点击或与微信胶囊冲突 | 单独规划美术矩形并完成多尺寸自动化预览，上线前补真机确认 | 自动化已验证，待真机确认 |
| 云集合未创建导致首次加载整体失败 | 玩家无法进入游戏 | 公告读取独立容错，主体数据优先 | 已验证 |
| 归墟歌者新增城墙时覆盖亡语 | 实际战斗效果错误 | 保留原 effect 并增加 guard，加入组合回归 | 已验证 |
| 初始化同步覆盖玩家数据 | 严重存档事故 | 只更新权威卡牌配置，不修改 `gameSaves` | 已验证 |
| 旧对局与新卡牌数据不一致 | 玩家困惑或对局异常 | 明确旧对局快照、新对局生效规则 | 已确认 |
| 误改设计文档中的历史提案表 | 丢失原始讨论与决策轨迹 | 不重建不存在的历史文件，由本文档维护最终权威记录与变更日志 | 已验证 |
| 公告先发布、卡牌数据尚未更新 | 公告内容与实际战斗不一致 | 固定采用“先迁移卡牌、后启用公告”的发布顺序 | 已文档化 |
| 前端伪造已读 ID 清除红点 | 玩家状态不可信 | 云函数只允许写入当前最新启用公告 ID | 已验证 |
| 旧玩家存档缺少 `uiState` 导致加载异常 | 老账号无法进入 | `normalize()` 为缺失字段补默认值并增加兼容测试 | 已验证 |
